## Q1. Does yt-dlp support Kick VODs and clips? What is its status, what is broken, and what about Cloudflare?

### Takeaway
yt-dlp has three Kick extractors: `kick:live`, `kick:vod` and `kick:clips`. In October 2026 the `kick:vod` extractor is **broken on the stable release**: since about July 2026 VOD metadata returns 404. The fix is PR #17322, still open as of late September 2026. Every Kick API call goes through curl_cffi browser impersonation. Cloudflare 403s have come back more than once and depend on the fingerprint and the IP's reputation. Because the pipeline already gets HLS master playlists from `/api/v2/channels/dylanjamesgg/videos`, it can skip the broken extractor and pass the m3u8 straight to ffmpeg or yt-dlp.

### Cited Findings
- **yt-dlp/yt-dlp**: https://github.com/yt-dlp/yt-dlp. 197.7k stars, Unlicense, last push 2026-10-10, not archived. Latest stable releases are 2026.08.19, 2026.07.04 and 2026.06.09, with no Kick lines in the visible changelogs. — [GitHub search API metadata](https://github.com/yt-dlp/yt-dlp); [releases](https://github.com/yt-dlp/yt-dlp/releases)
- `yt_dlp/extractor/kick.py` defines `KickBaseIE`, `kick:live` (`/api/v2/channels/{channel}`), `kick:vod` (`/api/v1/video/{uuid}`, which takes `response['source']` as the m3u8) and `kick:clips` (`/api/v2/clips/{clip_id}/play`, HLS or a direct URL). Every API call passes `impersonate=True`. The extractor reads the `session_token` cookie and sends it as a Bearer token, which matters for sub-only VODs. **There is no chat, live_chat or subtitle extraction for Kick.** — [kick.py source](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/yt_dlp/extractor/kick.py)
- **Open issue #17284** (22 Jul 2026), "[kick:vod] VOD metadata returning 404 Not Found due to recent site URL changes". The report quotes Kick Support saying "it changed how the URLs for VODs are generated". The issue is labelled `site-bug` and is still open. The workarounds in the thread are: (a) take the m3u8 from `kick.com/api/v2/channels/{channel}/videos`, which is the endpoint the pipeline already uses, or copy it from DevTools; (b) take a `.ts` segment URL, cut everything after `hls/` and append `master.m3u8`. Users also reported **ad problems**: a master m3u8 that downloaded only a 30-second pre-roll ad (9 Aug), and a VOD with mid-stream ad inserts that played only the intro ad (14 Sep). Issue #17428 ("Kick Streams Giving 404", 14 Aug 2026) was closed as a duplicate. — [issue #17284](https://github.com/yt-dlp/yt-dlp/issues/17284)
- **PR #17322 "[ie/kick] Rework extractors"** (by doe1080) closes #17284 and #15888. It is open, labelled `pending-fixes`, with changes requested on 18 and 25 Aug and fixes pushed on 27 Sep 2026. A tester reported "the endpoint fix works great, metadata resolves cleanly where stable just 404s". The same tester said VOD playback still returned 403 unless `--impersonate chrome` was passed, because the m3u8 fetch did not inherit `impersonate=True`. — [PR #17322](https://github.com/yt-dlp/yt-dlp/pull/17322)
- **Cloudflare history**: issue #16012 (Feb 2026), "Kick.com VOD downloads fail with HTTP 403", came from the `v1/video` API call. Maintainer bashonly said the cause was probably a curl_cffi fingerprint being blocked, or **IP reputation causing a JS challenge**. The fix, PR #16018 "[rh:curl_cffi] Deprioritize unreliable impersonate targets", was merged on 20 Feb 2026. bashonly also said the impersonate target is hardcoded in the extractor, so `--impersonate` cannot override it for API calls. Earlier issues: #14444, "Kick VOD download giving HTTP 403" (Sep–Dec 2025), and #13442, sub-only VODs (Jun 2025). — [issue #16012](https://github.com/yt-dlp/yt-dlp/issues/16012); [yt-dlp issue search results](https://github.com/yt-dlp/yt-dlp/issues?q=kick)
- **streamlink/streamlink**: https://github.com/streamlink/streamlink. 11.8k stars, BSD-2-Clause, last push 2026-10-11. Its Kick plugin matches live, VOD (`/{channel}/videos/{id}`) and clip URLs. For VODs it uses the newer `https://web.kick.com/api/v1/channels/{channel}/videos/{vod}` endpoint, with `channel_id` scraped from the page HTML. Clips use `kick.com/api/v2/clips/{clip}`. On an HTTP 403 it **launches Chromium through CDP to solve a JS challenge**, then caches the cookies and headers for 30 days. — [streamlink kick plugin](https://raw.githubusercontent.com/streamlink/streamlink/master/src/streamlink/plugins/kick.py)

### Inferences
- The most reliable download path for this pipeline is not to depend on `kick:vod`. Take the master m3u8 from the existing `/api/v2/channels/dylanjamesgg/videos` call, pick a rendition, and fetch only the 10-second `.ts` segments that cover the wanted range. Segment index = floor(t/10). Then remux with `ffmpeg -c copy`. This gives exact partial ranges without re-encoding and runs entirely on CPU. `yt-dlp --download-sections` on the raw m3u8 is a fallback.
- The ad reports in #17284 suggest some Kick VOD playlists now contain ad or discontinuity segments. The pipeline should check `#EXT-X-DISCONTINUITY` and ad markers in the media playlist and the expected duration, instead of trusting the playlist blindly.
- A cloud container runs on a datacenter IP, which per bashonly's IP-reputation comment is more likely to get Cloudflare JS challenges on `kick.com/api/*`. Have a fallback ready: curl_cffi with a Chrome target, or a headless-browser cookie refresh like streamlink's. Keep the Kick API calls few, since only the JSON API, not the segment CDN, has been reported as blocked.
- Clips: the `kick:clips` extractor was not named in the breakage reports found, so `yt-dlp <clip URL>` probably still works. The pipeline can also take `clip_url` from `/api/v2/clips/{id}/play` and fetch it directly.
- CPU-only: yes, everything here downloads or remuxes HLS. Integration difficulty from Python: low. yt-dlp is importable as a library (`yt_dlp.YoutubeDL`). Install curl_cffi alongside it, because the extractor needs impersonation.

### Gaps
- I did not confirm whether PR #17322 has merged since 28 Sep 2026, or whether a nightly build fixes VOD metadata.
- I could not check from yt-dlp's README in this session the exact pip extra (`yt-dlp[default,curl-cffi]`) or which curl_cffi version works best now.
- No source confirmed whether Kick's HLS segment CDN (as opposed to `kick.com/api`) is behind Cloudflare bot checks.

## Q3. Kick chat: VOD chat replay with timestamps, live chat logging, unofficial API wrappers, and the official Kick public API, SDKs and webhooks

### Takeaway
The **official Kick API (api.kick.com/public/v1) has no VOD, clip or chat-history endpoints.** For live chat it offers only a `chat.message.sent` webhook with `created_at` timestamps. **VOD chat replay is only available from an unofficial endpoint**: `https://kick.com/api/v2/channels/{channel_id}/messages?start_time=<ISO8601>`, which you walk forward with a time cursor. Several small repos use it, and one is still running daily in October 2026. Live chat can be logged either through the official webhook (needs a public HTTPS receiver and an OAuth app) or through Kick's unofficial Pusher websocket (no auth, used widely).

### Inferences
- **Recommended chat design.** (1) VOD chat replay: write a small Python poller like tourist1159's. Use curl_cffi (Chrome impersonation) instead of urllib for resilience to Cloudflare. Get `channel_id` and the VOD `start_time` from `/api/v2/channels/dylanjamesgg/videos` or `/api/v1/channels/dylanjamesgg`. Walk the cursor and store `created_at`, `sender.username`, `content` and emote IDs. Offset in VOD = `created_at - vod.start_time`. Then bucket messages per second to find spikes in "W", "LETS GO" and emote floods. (2) Live chat: since Dylan owns the channel, the official `chat.message.sent` webhook, received with kickcom.py's verified webhook server, is the ToS-safe option. It needs a publicly reachable HTTPS endpoint. The unofficial Pusher websocket (subscribe to `chatrooms.{chatroom_id}.v2`) needs no auth or public endpoint and is easier to run inside a container, but can change without notice.
- The replay endpoint is undocumented and depends on Cloudflare letting requests through, so any chat-spike feature should degrade gracefully, for example by falling back to the live chat log captured during the stream. Logging live chat during every stream is the more robust primary source.
- Avoid repos whose topics advertise Cloudflare/Kasada bypass reverse engineering (omkarcloud/kick-scraper, sarperavci) or view-bots (Kickerz) in a production pipeline tied to Dylan's account. Read-only polling without authentication does not put his account at risk, but self-bot login with session cookies (kick-js write mode) could.
- CPU-only: yes for all of these, since they are HTTP or websocket only. Integration difficulty: low for the replay poller and the Pusher logger (about 100 lines of Python). Medium for the official webhook, which needs an OAuth app, a public URL and signature verification.

### Gaps
- I did not find an official statement of how wide a time window each `messages?start_time=` response covers, its page size, or its rate limits. The stepping logic is taken from community code.
- I did not verify whether the official webhook can be subscribed with an app token for one's own channel without extra approval, or how reliably it delivers during high-traffic moments.
- I could not confirm whether the replay endpoint needs Cloudflare impersonation from a datacenter IP. tourist1159's stdlib script working from GitHub Actions in October 2026 suggests it often does not.

## Q4. Open-source social schedulers: platforms, APIs for scripted scheduled posts, self-hosting needs and licenses

### Takeaway
**Postiz (gitroomhq/postiz-app)** is the clear leader: 37k stars, AGPL-3.0, very active with v2.25.1 on 11 Oct 2026. It supports X, Instagram, TikTok and YouTube, and has a public REST API (`POST /public/v1/upload`, `POST /public/v1/posts` with `type: draft|schedule|now`, `date`, media). Its self-host stack is heavy: about 9 containers including Temporal and Elasticsearch. **BrightBean Studio** (2.5k stars, AGPL, Django, light) has a REST API and approval stages but **no X support**. **Mixpost** Lite (MIT) has only Facebook, X and Mastodon. Instagram, TikTok and YouTube need paid Pro. **TryPost** (704 stars, AGPL, Laravel) supports all four target platforms and has a REST API and MCP, but is younger.

## Q5. Platform API limits for posting: X tiers and costs, Instagram Reels requirements, TikTok Content Posting audit, YouTube Shorts uploads

### Takeaway
Every official route works for one owner-run account, but each has a catch. **X** charges per post (pay-per-use, about $0.015 per post and $0.20 if the post contains a URL, per secondary sources). **Instagram** needs a professional (Business or Creator) account, media at a public URL, and allows 100 API posts per 24 h. **TikTok** forces every post from an unaudited app to private (SELF_ONLY) until the app passes an audit. **YouTube** locks uploads from unverified API projects created after July 2020 to private until audited.

### Cited Findings
- **X**: the 2026 developer API is **pay-per-use** with prepaid credits. A standard post costs **$0.015 per request**, and a post containing a URL costs **$0.20**, a rate reportedly added in April 2026. Reads cost $0.005 per post returned. Legacy Basic and Pro are kept only for accounts subscribed before the cutover. Enterprise starts at $42k+/month. Most of these sources are vendor blogs (opentweet, bundle.social, Blotato) and should be checked against docs.x.com, which did not resolve here. — [MediaNama, Feb 2026](https://www.medianama.com/2026/02/223-x-developer-api-pricing-pay-per-use-model/); [bundle.social, Jul 2026](https://bundle.social/blog/x-api-pricing-2026-costs-limits); [opentweet pricing](https://opentweet.io/x-api-pricing)
- **X media upload**: X deprecated the v1.1 `media/upload` endpoints. Dates given are 31 Mar 2025 (planned) and 9 Jun 2025 (Emplifi). The replacement is `api.x.com/2/media/upload`, which uses the same INIT/APPEND/FINALIZE flow but needs OAuth 2.0 user context with the `media.write` scope. **Conflicting**: 2026 posts from Ayrshare and bundle.social say the v1.1 `upload.x.com/1.1/media/upload.json` path signed with OAuth 1.0a is still used. — [Emplifi](https://docs.emplifi.io/platform/latest/home/x-formerly-twitter-media-upload-v1-1-api-endpoints); [Make community](https://community.make.com/t/please-upgrade-to-support-x-api-v2-media-upload-endpoints/75409); [bundle.social](https://bundle.social/blog/x-api-post-tweet); [Ayrshare](https://www.ayrshare.com/blog/top-7-tips-and-tricks-for-twitter-api-posting/)
- **Instagram (Reels via Graph API)**: only professional accounts. Permissions are `instagram_basic` and `instagram_content_publish` (or `instagram_business_content_publish` with Instagram Login), which need App Review "for users without a role on your app". Meta fetches media by URL ("it must be on a public server"). The limit is **100 API-published posts per 24 h** (Meta page updated 30 Jun 2026; older copies say 50), and `GET /<IG_ID>/content_publishing_limit` reports usage. There is also a cap of **400 containers per 24 h**. Reels are single-media posts and cannot go in carousels. A professional account tied to a Page that requires Page Publishing Authorization cannot publish until PPA is done. — [Meta content publishing (via search summary)](https://developers.facebook.com/docs/instagram-platform/content-publishing); [bundle.social Instagram guide](https://bundle.social/blog/instagram-graph-api)
- **TikTok Content Posting API**: "posts from unaudited clients are kept in private viewing mode". Posting to a public account returns `unaudited_client_can_only_post_to_private_accounts`. Secondary source (Postiz docs): before audit `privacy_level` is forced to `SELF_ONLY`, and Direct Post is limited to 5 users per 24 h, who must have private accounts. A third party estimates audit turnaround at 2–6 weeks. — [TikTok Direct Post reference](https://developers.tiktok.com/doc/content-posting-api-reference-direct-post); [TikTok get started](https://developers.tiktok.com/doc/content-posting-api-get-started); [Postiz TikTok provider doc](https://docs.postiz.com/providers/tiktok.md); [bundle.social TikTok approval](https://bundle.social/blog/tiktok-api-approval)
- **YouTube Data API `videos.insert`**: "uploads from unverified API projects created after July 28, 2020 are restricted to private viewing mode" until the project passes an audit. **Quota cost conflicts**: the official page says 100 units, third parties cite 1,600 units on a 10,000-unit daily default, and one claims a separate 100-uploads/day bucket since June 2026 (unverified). — [videos.insert (developers.google.cn mirror)](https://developers.google.cn/youtube/v3/docs/videos/insert); [Ayrshare unverified-app guide](https://www.ayrshare.com/solutions/google-api-error-403-unverified-app-how-to-fix-the-audit-pipeline/); [Postproxy](https://postproxy.dev/blog/automate-youtube-uploads/)

### Inferences
- At 1–3 X posts a day the pay-per-use cost is small (well under $5/month), but captions should not include links (e.g. a Kick URL), or each post costs about 13 times more. Put the link in a reply or in the bio instead.
- Instagram does not take a scheduled publish time through the API. The scheduler, whether Postiz or a cron job, has to call publish at 2pm itself, and the video must be reachable at a public HTTPS URL when the container is created. A private Google Drive link will not work unless it is turned into a direct public URL. Upload to Postiz or object storage first.
- For a single owner-operated account, adding Dylan's Instagram and TikTok accounts as app roles or testers avoids full App Review on Meta. TikTok still requires its audit before posts can be public, so plan TikTok as a "post as draft/inbox and publish manually in-app" flow, or budget weeks for the audit. YouTube Shorts needs either an audited project or accepting private uploads that are then made public by hand.
- These limits apply whether you use Postiz, BrightBean, TryPost or direct libraries, because they all use your own developer apps.

- I could not reach docs.x.com, developers.facebook.com or developers.tiktok.com directly. The X prices, the Instagram 100-post limit and the TikTok 5-user cap come from search summaries or secondary sources and should be checked before budgeting.

## Q6. Lightweight libraries for posting directly (no scheduler), and the ToS and ban risk of unofficial clients

### Takeaway
For direct posting from Python, use the official APIs: **tweepy** (or X's own `xdk` SDK) for X, raw Graph API calls with `requests` for Instagram Reels, the **google-api-python-client** for YouTube, and TikTok's Content Posting API over HTTP. Unofficial clients such as **instagrapi** (Instagram private API) and the TikTok browser and requests uploaders work today, but carry account-ban and checkpoint risk. instagrapi's own README now says it is for "testing, research, and controlled internal automation".

### Inferences
- **Minimal no-scheduler stack** (CPU-only, Python): an APScheduler or cron job in the pipeline container fires at the approved time. X: tweepy or xdk does a chunked video upload and then creates the post. Instagram: `requests` POSTs `/{ig-user-id}/media` with `media_type=REELS` and `video_url=<public URL>`, polls `status_code`, then calls `media_publish`. YouTube: `google-api-python-client` `videos().insert` with a resumable upload. Integration difficulty is medium overall. - Avoid instagrapi and the TikTok uploaders for Dylan's main accounts. Logins from datacenter IPs in a cloud container are the classic trigger for Instagram checkpoints and bans, and TikTok uploaders that replay browser sessions break the platform terms. If they are used at all, use them only on a throwaway or test account.
- Since tweepy's maintenance pace has slowed (last push July 2026) and X's media endpoints have shifted, check that tweepy works with the current media upload path before relying on it. X's xdk-generated SDK may follow API changes faster.
